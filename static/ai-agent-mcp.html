MCP: standarden som kopplar agenten till era system

Model Context Protocol är det som gör att ni kan byta ramverk utan att bygga om integrationerna. Här är vad det är, hur en MCP-server ser ut i praktiken, och vad ni måste tänka på innan ni kopplar in en ni inte själva skrivit.

Kort version

En MCP-server beskriver era system en gång. Sedan kan vilken MCP-kompatibel agent som helst använda dem – oavsett modell och ramverk.

Det låter tråkigt. Det är det viktigaste beslutet ni fattar, eftersom det är integrationerna som kostar. Byter ni ramverk byter ni loopen; verktygen följer med.

Problemet MCP löser

Före MCP såg verkligheten ut så här: ni byggde en integration mot ert affärssystem för agenten i OpenAI:s SDK. Sedan ville ni prova Claude, och fick skriva om den. Sedan ville någon bygga något i n8n, och fick skriva om den igen. Tre kopior av samma integration, alla med sin egen bugg.

Utan MCP

Antal integrationer = antal system × antal ramverk. Fem system och tre ramverk blir femton integrationer att underhålla, och ett byte av ramverk innebär att bygga om allt.

Med MCP

Antal integrationer = antal system. Fem system blir fem MCP-servrar, som alla ramverk kan använda. Ett byte av ramverk rör inte integrationerna.

Det är hela poängen. Allt annat i det här dokumentet är detaljer kring den ekvationen.

De tre sakerna en MCP-server exponerar

En MCP-server är i grunden en JSON-RPC-process. Den erbjuder tre sorters saker, och i praktiken använder de flesta bara den första.

1. Verktyg (tools) ← det ni kommer använda

Funktioner agenten får anropa: hamta_kund, skapa_arende. Varje verktyg har ett JSON Schema för sina indata. Det är här nittio procent av värdet ligger.

2. Resurser (resources)

Data agenten får läsa, adresserad med URI: ett dokument, en tabell, en logg. Skillnaden mot ett verktyg är att en resurs hämtas, inte utförs. Användbart, men de flesta klarar sig med ett läsande verktyg i stället.

3. Promptmallar (prompts)

Återanvändbara instruktionsmallar som servern erbjuder klienten. Minst använda delen. Hoppa över den tills ni har ett konkret behov.

Så ser en MCP-server ut

Det här är inte ett utdrag – det är hela servern. Om ni trodde att MCP var ett stort åtagande är det här den nyttigaste bilden på sidan.

# En komplett MCP-server. Det här är hela det minsta exemplet.
# pip install mcp

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("affarssystem")


@mcp.tool()
def hamta_kund(kundnummer: str) -> dict:
    """Hämtar kunduppgifter ur CRM.

    Använd när användaren nämner ett kundnummer eller kundnamn.
    Returnerar namn, org.nr, avtalsform och kontaktperson.
    """
    return crm.sla_upp(kundnummer)


@mcp.tool()
def skapa_arende(kundnummer: str, rubrik: str, beskrivning: str) -> str:
    """Skapar ett nytt supportärende och returnerar ärendenumret.

    Skapa ALDRIG ett ärende utan att först ha hämtat kunden med
    hamta_kund. Vid osäkerhet om rubriken: fråga användaren i stället.
    """
    return arendesystem.skapa(kundnummer, rubrik, beskrivning)


if __name__ == "__main__":
    mcp.run()          # stdio som standard

Lägg tiden i docstringen, inte i koden

Texten under varje funktion är inte dokumentation för er – det är instruktionen modellen läser när den avgör om verktyget ska användas. Lägg märke till vad de två exemplen ovan gör:

  • De säger när verktyget ska användas, inte bara vad det gör.
  • De säger vad som returneras, så agenten vet om den fått svaret.
  • De säger vad agenten ska göra vid osäkerhet – fråga, inte gissa.
  • De uttrycker ordningsberoenden ("skapa aldrig ärende utan att först ha hämtat kunden").

En slarvig beskrivning ger en agent som väljer fel verktyg, och det felet ser ut som att modellen är dum. Den är inte dum – den är dåligt instruerad.

Stdio eller HTTP?

Det finns två transporter, och valet är enklare än det verkar.

Transport Använd när Att tänka på
stdio Servern körs som en lokal process bredvid agenten Enklast. Ingen nätverkssäkerhet att tänka på, men skalar inte över flera maskiner.
Streamable HTTP Servern ska nås över nätverk, av flera agenter eller från CI Kräver autentisering och behörighetskontroll. Specifikationen 2026-07-28 tog bort den statefulla handskakningen, så nya servrar kan byggas tillståndslösa – vilket är det som gör dem skalbara.

Börja med stdio. Flytta till HTTP när ni faktiskt har flera konsumenter – och bygg då tillståndslöst från början, enligt den nyare specifikationen.

Säkerhet: det ni måste veta innan ni kopplar in något

Det finns fler än 9 400 publika MCP-servrar. Det är ekosystemets styrka och dess största risk samtidigt. MCP är ett protokoll – det är varken säkert eller osäkert i sig. Riskerna ligger i vad ni kopplar in och med vilka behörigheter.

Verktygsförgiftning

Verktygsbeskrivningen är text som modellen litar på. En manipulerad beskrivning kan innehålla instruktioner som får agenten att göra något annat än avsett – och den texten syns inte i något gränssnitt. Motmedel: kör bara servrar ni själva byggt eller läst igenom.

Behörighet som smittar

En agent som når både er kunddatabas och ett verktyg som skickar mejl kan förmås att kombinera dem. Varje enskilt verktyg är ofarligt; kombinationen är det inte. Motmedel: minsta möjliga behörighet per server, och tänk igenom vad verktygen kan göra tillsammans.

Servern som ändrar sig

En extern server kan ändra sina verktygsbeskrivningar efter att ni granskat dem. Motmedel: lås versioner, kör känsliga servrar själva, och logga vilka verktyg som faktiskt anropades vid varje körning.

Grundregeln är densamma som för alla beroenden, men konsekvensen är större: ett vanligt bibliotek gör vad koden säger, en MCP-server påverkar vad agenten bestämmer sig för att göra. Läs vidare i guiden om agentsäkerhet.

MCP, A2A och ACP – vad är vad?

De tre nämns ofta i samma andetag och löser olika problem.

  • MCP – agent mot verktyg. Hur agenten når era system. Det här är det ni behöver först, eftersom problemet nästan alltid är att nå befintliga system.
  • A2A – agent mot agent. Googles protokoll för hur två separata agenter utbyter uppgifter. Relevant först när ni har flera agenter från olika leverantörer som ska samarbeta.
  • ACP – agent mot agent, REST-baserat. Alternativ från IBM och AGNTCY. Mindre spritt.

Praktiskt råd: bry er om MCP nu. A2A när ni faktiskt har två agenter som behöver prata – och läs först varför ni antagligen inte ska ha två agenter.
